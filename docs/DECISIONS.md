# Decisions

- 2026-09-06: Preserve the requested pnpm workspace, strict TypeScript, React/Vite, Node LTS/Fastify and PostgreSQL stack. The mandatory first implementation slice is synthetic eligibility → reference cryptographic ballot → threshold tally → offline verification.
- 2026-09-06: GitHub account `Lontkovsky` is explicitly authorized by the request. Create a new public repository; no existing private code or history is reused.
- 2026-09-06: Production identity providers have no supplied technical contracts or credentials. Their boundaries will be visible as AwaitingProviderContract, never silently substituted with mocks.
- 2026-09-06: Belenios 3.3.0 source is being inspected at upstream commit `337887bd1862c7cd057080b530fd80941bfc3c69`; selection remains subject to compatibility evidence. Cryptographic formats and proofs will not be reimplemented in TypeScript.
- 2026-09-06: Select unchanged Belenios 3.3.0 with its fixed unweighted registry and mandatory trustee plus 2-of-3 threshold. Admission of genuinely new people after opening remains explicitly unfulfilled in #41.
- 2026-09-06: Synthetic ceremony retry is a durable operation: exact manifest, roster and key material are reused. Identity and ballot registration accept only an identical immutable registration. Intermediate ceremony material is removed after management commits; separate local test trustee files remain. Local custody is a simulation, not organizational independence.
- 2026-09-06: Identity session tokens stay only in React memory and are never attached to ballot requests. Recovery reissues the same sealed credential. A verified provider-attribute conflict revokes the identity session; it cannot erase an already exported Belenios credential from a frozen public registry. This residual risk must remain visible in revocation documentation.
- 2026-09-06: Trustee CLI checks a pretrusted public signer and election hash, contiguous checkpoint signatures, immutable final archive, exact receipt set, reference proofs, close time and minimum group size. It binds itself durably to one final set before computing a share. Enough compromised key holders can bypass an honest CLI; the client guard does not prevent their collusion.
- 2026-09-06: The user requires the existing in-app Browser exclusively. CLI/API/native tests do not count as browser E2E. A reusable E2E coordinator must accept that existing Playwright binding and must not start Chromium or another browser session.
- 2026-09-06: Result exports extend the existing strict result object. CSV uses one documented `field,json_value` representation so arbitrary question text and nested policy/count types round-trip exactly without hidden apostrophe/tab prefixes. SVG carries that same object in metadata and displays the full methodology. Publication gates are shared with the JSON endpoint; native proof verification remains separate. See `docs/PUBLIC_RESULTS.md` for format and interpretation boundaries.
- 2026-09-06: The observer requires an explicit previously authenticated poll/key/hash configuration and an explicit initial state creation. Checkpoints and known acknowledgements remain separate from full content; local state stores minimal signed evidence. Published tally verification always invokes the original native core. Comparing two retained histories is an explicit command, with no claim of fork detection during complete observer isolation. Missing local state and failed checks never reset history. See `docs/OBSERVER.md`.
- 2026-09-06: Partial decryption intake must call the unchanged Belenios library's `check_factor` before storage. The original CLI lacks that standalone operation, so a small native transport exposes the same check used by its server; no cryptographic primitive or reference format is rewritten. A trustee's first self-consistent signed history still needs external acknowledgement evidence to establish completeness. See `docs/TRUSTEE_VERIFICATION.md`.
- 2026-09-06: Admission regression fixtures use original native credential generation and archive commands. Distinguish rejection against an already committed roster from acceptance after replacing the trusted roster itself. The latter is explicit evidence of a trust-root limitation and does not count as an implemented anti-stuffing control. The test expansion changes no production behavior; see `docs/ADMISSION_VERIFICATION.md`.
- 2026-10-30: The canonical repository is `Lontkovsky/openvote`. The Ukrainian product name remains «Відкритий голос» and the English name is Open Vote.
- 2026-10-30: The owner superseded the bilingual product-name decision above. The single canonical product brand is `OpenVote`; the repository slug, domain and established technical identifiers remain unchanged.
- 2026-10-30: The Render synthetic demo uses one paid Docker service but preserves separate browser origins through exact Nginx host routing: apex web, identity, ballot and management. A same-origin `/api/*` gateway was rejected because it would collapse the explicit identity/ballot-origin boundary. Providers, service processes and Belenios bridges remain loopback-only; three databases keep storage roles separate.
- 2026-10-30: Render runtime initialization is fail-closed. An empty disk is accepted only with three empty databases; keys/configuration are generated once and marked ready only after migrations. Missing, partial or rebound persistent state stops startup. This is a synthetic hosted demo under one operator, not production readiness or independent key custody.
- 2026-10-30: The initial public launch is a separate demand-validation surface, not the full voting platform. It uses one web service, one PostgreSQL database and one same-origin API. A server-generated browser credential is stored as a host-only HttpOnly SameSite=Strict cookie; each response row contains only the poll ID and version, its SHA-256 hash and one immutable answer. This reduces accidental repeats but does not establish a unique person, citizenship, bot resistance or representativeness. Current counts stay unpublished during collection.
- 2026-10-30: One root Render Blueprint owns one `production` environment with one `openvote` web service, four databases and one 1 GB persistent disk. During demand collection the service uses only `openvote-demand`; the identity, ballot and management databases are suspended operationally because Blueprint YAML has no declarative suspension field. The attached disk is not demand storage and remains uninitialized until the later full-platform cutover switches the same service to the full image/configuration, resumes the three role databases and suspends the demand database. Full cryptographic runtime verification is deferred until that cutover.
- 2026-10-30: The owner explicitly superseded the initial unpublished-count policy for the separate demand-validation poll. Its existing versioned GET and successful POST receipt now expose only the total accepted responses and an exact three-number tuple ordered as `Підтримую`, `Не підтримую`, `Утримуюсь`; no percentages, credential hashes or row-level records are public. These live small-group counts permit before/after differencing, while the page continues to state that responses do not establish unique people, citizenship or representativeness. The full platform's rule against publishing interim formal-vote distributions remains unchanged.
- 2026-10-30: The demand landing is action-first: the confirmed question and vote action precede product explanation, while one concise notice retains the self-selection, identity/citizenship, repeat-browser and non-representativeness boundaries. A single silent same-origin walkthrough is assembled from real local synthetic create, vote and published-result screens. It does not autoplay, embed a third party, expose identity selection or claim that the prototype is production ready.
- 2026-10-31: The demand landing adds one server-side assistant grounded only in the shared nine-item FAQ. The same-origin route requires the existing demand credential and exact Origin, transmits only the typed question plus static FAQ context, disables provider-side response storage and tools, and bounds input, output, timeout, per-credential requests, global requests and concurrency. OpenVote stores no chat text. The owner selected one floating dialog named `Тарас` and explicitly removed the rejected inline form, assistant subtitle and service note. The required server secret has no default and must exist on the current Render service before deployment.
- 2026-10-31: Catalog-capture limits are keyed only by the deduplicated author pseudonym, never by IP address or voting history. The development configuration permits six draft/review items, three publications per 24 hours, a 60-second publication cooldown and two simultaneously open or scheduled polls. Moderator approval checks the publication limits while holding the existing per-author advisory lock.
- 2026-10-31: A duplicate or rejection is a reasoned methodological review, not silent deletion. Only a moderator may record or resolve that decision. An appeal preserves both reasons in the event journal; reopening is permitted only from `Rejected` and returns the proposal to `Draft` with methodology pending.
